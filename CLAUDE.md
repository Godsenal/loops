# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Loops** — a multi-loop autonomous-agent platform. Each "loop" is a recurring, headless Claude Code agent for one domain (SEO, dead-code cleanup, webview refactor, …). A loop's **orchestrator** discovers work and fans it out; **workers** each implement one item and open a PR. **Humans merge** — the engine never merges, deploys, or force-pushes.

The engine is shared; a loop differs only in its `mission.md` (what to find, how) and `config.json` (repo / Linear / schedule / concurrency).

There is **no build, test, or lint step**. The engine is **zero dependencies** — `zsh` scripts + Node built-ins (`http`, `child_process`, `fs`); don't go looking for `package.json`, a test runner, or CI for this repo; there is none. **One exception, dashboard UI only:** the dashboard vendors [Oat UI](https://oat.ink) (MIT, ~10KB) as pinned static assets in `vendor/oat.min.{css,js}` — served by `dashboard-server.mjs` at `/vendor/*` and loaded by `dashboard.html`. **This is still no-build** (edit `dashboard.html` → refresh; no bundler, no `npm install`, `dashboard-server.mjs` stays Node-builtin-only). To bump Oat, re-`curl` a pinned version from `unpkg.com/@knadh/oat@<ver>/` into `vendor/` (Oat is sub-v1 — pin, don't float).

## Hard prerequisite: cmux

The platform is built on **cmux** (a terminal with socket control). The dispatcher and dashboard run *inside cmux panels*, and workers spawn as *live cmux tabs*. Non-cmux environments are unsupported. `claude`, `gh`, `node`, `git` must also be present.

## Commands

```sh
./install.sh                 # detect tools → write loops.env, ~/.loops-home, symlink create-loop skill
./loopctl dashboard          # dashboard at http://localhost:8422 (opens a cmux panel)
./loopctl start              # start the global dispatcher (cmux panel)
./loopctl stop|pause|resume|status
./loopctl run-now <loop-id>  # fire one orchestrator cycle for a loop immediately
```

There are no unit tests. To exercise a change, run a single orchestrator cycle directly:

```sh
LOOP_MODE=full ./bin/run-once.sh <loop-id>      # full cycle (headless claude -p), logs → loops/<id>/state/run.log
LOOP_MODE=reconcile ./bin/run-once.sh <loop-id> # only merge-cleanup + snapshot (fast)
node ./bin/render-prompt.mjs <loop-id> orchestrator   # inspect the rendered prompt without running it
```

`LOOP_MODE` is `full` (default) | `audit_only` (skip fan-out) | `reconcile` (only STEP 1 merge-cleanup + STEP 4 snapshot) | `retro` (performance analysis → update `state/learnings.md`; uses `retro-base.md`, no discovery/fan-out).

## Architecture

The runtime is a chain of processes, each launched in a fresh/empty context. **All cross-run continuity lives in the Linear ledger, not in memory.**

```
dispatch.sh (cmux panel, loops while-true)
  └─ per enabled loop, on schedule → spawn-orchestrator.sh <id>   (FOREGROUND — must keep cmux socket access)
       └─ run-once.sh <id>   (claude -p <rendered orchestrator prompt>, headless, in the loop's orchestrator worktree)
            └─ orchestrator fans out → spawn-worker.sh <id> <issue>   (one per Backlog item, up to cap)
                 └─ new cmux tab runs worker-run.sh → claude <rendered worker prompt>   (live TUI, dedicated worktree+branch)
                      └─ worker implements 1 issue → /gbase:go --no-review (polish+PR) → preview check → resident /gbase:monitor watch until merge/close (unattended rules; still never merges)
```

- **`bin/_common.sh`** — sourced by every script. Derives `LOOPS_HOME` from its own location (`bin/`'s grandparent) and sources `loops.env`. This is why the repo works wherever it's cloned: paths are dynamic, never hardcoded.
- **`bin/render-prompt.mjs`** — the templating core. Combines `bin/{orchestrator,worker,verifier,validator,retro}-base.md` (the shared engine logic) + the loop's `mission.md` + `state/learnings.md` (`{{LEARNINGS}}`, retro-accumulated lessons) + `config.json` values, substituting `{{VAR}}` tokens. Editing engine behavior = editing the `-base.md` files, not the per-loop files.
- **Feedback layer (closes the loop; all opt-in via config, all deterministic-guarded):**
  - **Resident monitor (pr-mode default).** The worker does **not** stop after opening its PR: after preview check / Linear In Review / verifier spawn, it stays in `/gbase:monitor` until the PR is MERGED/CLOSED, auto-applying mechanical CI fixes and mechanical/explicit review comments in-session (non-force push only). The worker prompt (`render-prompt.mjs` `WORKER_DELIVERY_PR` step 7) overrides the skill's interactive behavior for unattended tabs: no merge/approve/close, **no `--force-with-lease`** (conflicts resolved only via non-force `git merge origin/<prBase>`, otherwise surfaced as comments), **no AskUserQuestion** (ask-gate situations → PR reply + Linear "🚧 사람 판단 필요" comment, keep watching), `--no-review` (monitor's self-review pass is AskUserQuestion-gated; the verifier is the loops-native checker), and no tab retitle (🛠/↩ is the engine's liveness signal). The gbase skills themselves are never modified. Watchdog's DELIVERED gate means a PR-open issue is never wedge-checked, so the idle watch causes no false positives; live-TUI cost of the resident session is unmeasured (same scope as workers). If the session dies (usage limits, cmux restart), the paths below take over — graceful degradation to the pre-resident behavior.
  - **`bin/rework-worker.sh`** — when a human reviewer leaves `CHANGES_REQUESTED` on an open PR **or** the verifier records a ❌ fail verdict, respawns the worker in its **preserved worktree** (`LOOP_REWORK=1` → worker-run injects a rework block: address explicit requests only, non-force push, reply to comments, then re-enter the resident monitor watch). With the resident monitor alive this never fires (live-tab dedup) — it is the **dead-session fallback** that also re-establishes the watcher. Orchestrator STEP 1 calls it for every OPEN PR unconditionally — 3 built-in guards make that safe: new-feedback gate (won't refire until a review/verdict *newer* than the last rework), per-issue cap `LOOP_REWORK_MAX` (default 2, then `rework-exhausted` surfaces to dashboard/bot), live-tab dedup. Orchestrator STEP 1's direct mechanical-CI-fix is gated on the same signal: it only touches the branch when rework's output shows no live tab (avoids racing the resident session). State: `state/rework.json`.
  - **`bin/spawn-verifier.sh` + `verifier-run.sh` + `verifier-base.md`** (config `"verify": true`, pr-mode only) — maker/checker split: after the worker opens a PR it spawns a **fresh-context verifier** in a detached `-vf` worktree (🔎 tab) that grades the PR against the issue's acceptance criteria, actually runs repo checks, and posts an evidence-backed verdict (✅ pass / ⚠️ concerns / ❌ fail) to PR + Linear + `state/verify/<ISSUE>.json`. The verifier **cannot edit code** — Edit/Write are blocked via `--disallowedTools` (structural, not prompt). fail → rework path above. Never merges/moves Linear states.
  - **`bin/spawn-validator.sh` + `validator-run.sh` + `validator-base.md`** (config `"validate": true`; proposal-type loops — see `docs/factory.md` M2) — discoverer/skeptic split: after each orchestrator run, `run-once.sh` deterministically spawns a **fresh-context validator** (detached `-vd` worktree at `baseRef`, 🧪 tab) for every un-judged human-gate proposal issue in the snapshot. It re-verifies the proposal's evidence for real (WebFetch reproduction, repo grep, competitor URLs), runs a distilled YC-style demand diagnostic (specificity / interest≠demand / status-quo-as-competitor / wedge / distribution), challenges premises against `vision.md`, must propose one cheaper alternative, and records a verdict (🟢 strengthen / 🟡 narrow / 🔴 reject) to Linear + `state/validate/<ISSUE>.json` — surfaced next to `gate.ask` in the dashboard gate modal and as a 🧪 badge. Edit/Write blocked structurally; never approves/rejects (the human gate does), never moves Linear states. Skips if a verdict or a human decision (`decisions/<ISSUE>.md`) already exists.
  - **실측 층 (`bin/measure-browser.mjs` · `measure-lighthouse.mjs` · `measure-run.mjs` · `preview-url.mjs`; config `measure` 블록)** — 발굴과 검증의 근거를 **코드 정적 신호에서 실제 브라우저 측정으로** 올린다. 측정은 결정론 쉘, LLM은 판정만 (`linear-*.mjs`와 같은 층 분리) — LLM에게 "브라우저로 확인해봐"를 시키면 run마다 근거가 달라져 회귀 추적이 불가능해진다.
    - **`measure-browser.mjs <url>`** — ego-browser(ego lite) CLI 래퍼. Bash 헤레독만 쓰고 파일을 안 쓰므로 **verifier의 `--disallowedTools Edit Write` 가드를 유지한 채** 쓸 수 있다. 수집: HTTP 4xx/5xx · `Network.loadingFailed` · JS 예외/unhandledrejection · console.error · **GraphQL `errors[]`**(fetch 훅 — GraphQL 실패는 HTTP 200이라 상태코드만 보면 "에러 0건 + 스켈레톤 화면"이라는 무음 실패를 놓친다) · 렌더 결과 · 스크린샷 · Navigation Timing. 훅은 `Page.addScriptToEvaluateOnNewDocument`로 심는다 — 로드 후 `js()`로 심으면 다음 내비게이션에서 사라져 **항상 "에러 0건"** 이 나온다. **고정 sleep 금지**(같은 URL이 12초엔 스켈레톤, 20초엔 정상 렌더로 실측됨): 준비 조건을 폴링하고 `readyMs`를 남긴다. 폴링 전 `about:blank`로 한 번 끊는다 — 탭을 재사용하면 **직전 문서가 살아 있는 채로** 첫 폴링이 "이미 렌더됨"을 오판한다.
    - **로그인 주입** (`measure.login` → `loops/<id>/login.json`, `/loops/`가 통째로 gitignore라 토큰이 레포에 안 들어간다) — `{origin, localStorage:{key:value}}`를 origin 진입 후 심는다. realty-webview는 배포 preview 번들에 시크릿을 bake 하지 않고 **dev 툴의 localStorage 주입을 전제로** 설계돼 있어(`realty-dev#testLoginInfoList`), 이 한 줄로 배포된 preview가 인증 상태로 뜬다(주입 전 root 0자 스플래시 → 주입 후 82KB 정상 렌더). 엔진은 키·값 스키마를 모른다(앱별 지식은 config에만).
    - **`measure-lighthouse.mjs <url>`** — `npx lighthouse@12`(설치 없음, 1회 ~23초, 버전 핀 고정 — 버전이 뜨면 audit id·기준이 바뀌어 과거 스냅샷과 비교 불가). ⚠️ **결정론과 노이즈를 분리해서 내보낸다**: 같은 URL 2회 연속 실측에서 perf 50 vs 78 · LCP 8722ms vs 2291ms · CLS 0 vs 0.121 인 반면, a11y/bp/seo 점수는 동일 · total bytes 0.01% 차 · requests 동일이었다. 따라서 **게이트(이슈 발행·verdict fail)는 `stable` 블록(점수·바이트·요청 수·실패 audit)에만** 걸고 `timings`는 코멘트용 참고치다. perf audit도 바이트 기반만 stable로 취급한다. 이 구분을 무너뜨리면 루프가 노이즈로 이슈를 만들고 rework를 무한 유발한다.
    - **`measure-run.mjs <loop>`** — config `measure.routes`를 순회해 위 둘을 돌리고, **직전 같은 label 스냅샷과 diff해서 findings를 산출**(`not-rendered`·`js-error`·`api-error`·`http-error`·`console-error`(신규만)·`audit-regression`·`bytes-regression`·`requests-regression`·`score-regression`, severity 부착). 상태 `state/measure/{<ts>-<label>.json, latest-<label>.json, shots/<route>.png}`(label별 20개 롤링). 전역 락 `/tmp/loops-measure.lockdir`으로 **측정을 직렬화**한다 — 워커·검증자가 병렬로 도는 플랫폼에서 동시 측정은 서로 CPU를 뺏어 렌더 폴링을 타임아웃시킨다. 락 실패·ego-browser 부재·login 파일 부재는 전부 **비0 종료**(무음 통과 금지 — "측정 못 했는데 조용히 빈 결과"가 검증을 통과로 둔갑시킨다).
    - **PR A/B 검증** — `preview-url.mjs <loop> <issue>`가 PR 코멘트에서 preview URL을 뽑고(브랜치명으로 **조합 금지**, 못 찾으면 비0 — "PR URL은 `gh pr view`에서만" 관례와 같은 이유), 같은 label로 **기준선 → PR** 순서로 `measure-run`을 두 번 돌리면 두 번째 출력의 findings가 곧 "이 PR이 바꾼 것"이다. `render-prompt.mjs`가 `measure` 블록이 있는 루프에만 `{{VERIFY_RECIPE}}`를 verifier 프롬프트에 주입한다(없으면 빈 문자열 = 기존 검증 동작 그대로, 하위호환). `--routes`로 관련 화면만 재는 게 필수 — 전 라우트 A/B는 20분 이상이라 무인 검증에 못 쓴다.
    - 전제: **ego lite 앱 설치 + 온보딩 완료**(`ego-browser`가 `~/.local/bin`에 등록되고 그 경로가 `LOOPS_PATH_PREPEND`에 있어야 헤드리스 run에서 보인다), Chrome 설치(Lighthouse가 띄운다). 첫 사용 loop: `webview-qa`(🔬, 아래).
  - **`vision.md`** (per-loop, optional, human-owned like `mission.md`) — product direction (target user / north star / core assets / non-goals) injected as `{{VISION}}` into orchestrator·retro·validator prompts. Split from mission so retro can never touch direction; editable in the dashboard ⚙️ modal (`save-vision`, `GET /api/mission?vision=1`). Empty/absent → block omitted entirely.
  - **`bin/event-poll.sh`** (config `on:{ciFailure,prReview,linearNew}`) — dispatch.sh polls ≤60s and pulls `next_fire` to now on: new CI failure on `prBase`, new human review on loop PRs, new Backlog issue in the Linear project. No new execution path — firing stays in the dispatcher's existing loop; every trigger is recorded in `runs.jsonl` (`event:"trigger"`). Cursors in `state/events.json` (first poll seeds silently).
  - **`bin/retry-backoff.sh`** — the orchestrator cycle was the **only link in the chain with no retry**: `run-once.sh` calls claude exactly once, so a transient failure idled the whole loop until its next schedule (3h for the webview loops). Measured over 5 days: 95 `Connection closed mid-response`, 62 `529`, 6 5xx/timeout — all of which succeed on a retry a minute later. Called from the same ≤60s block as event-poll (shared PAUSED/enabled gate) and uses the **same mechanism — pull `next_fire`** — so there is no new execution path and the cap/budget/drain gates still apply. Classification is what matters, and it follows from `claudeCmd` being `claude-acct cloop` (account round-robin): **transient** (connection-closed·529·overloaded·5xx, plus exit 137/143/124 which leave no text in run.log) → retry; **per-account** (`Not logged in`·`Invalid API key`·`Credit balance`) → retry, because the limit-marker hook only fires on **429**, so this class gets no cloop handoff and dies on one account — the next call round-robins onto a different one and just works; **exhausted** (weekly/session limit) → **no** retry, since cloop already walked every enabled account inside that one call (`account_alert` surfaces it instead); **anything else** → no retry, left to incident-bridge's cycle-error filing. Backoff `LOOPS_RETRY_BACKOFF`("60 300 900"), cap `LOOPS_RETRY_MAX`(3), reset by any `exit 0`. State `state/retry.json` keyed on `lastRunDone` so each finished run is judged exactly once; skips while the run lock is held, and never *delays* a schedule that is already sooner (that case also doesn't consume an attempt). Writes only `next_fire` + a `runs.jsonl` `trigger:"retry"` record.
  - **`bin/record-cost.mjs`** — every headless run (`run-once.sh` cycles, verifier, validator) executes claude with `--output-format json`; this splits the output into the human-readable `run.log` text + a `state/costs.jsonl` usage record. `dashboard-server.mjs` aggregates it as per-loop `economics` (today/total USD, cost per merged, merge-rate, rework count); config `budget:{dailyUsd}` is a **soft cap** — dispatcher skips fires while today's sum ≥ cap (in-flight workers untouched, resets at midnight). Live-TUI worker cost is *not* measured (headless-only scope, labeled as such in the UI) — this now includes the resident monitor phase, which extends each worker session's unmeasured lifetime until merge.
  - **Self-healing platform layer (process-level — closes the "engine itself died" gap).** All other recovery (watchdog/reaper/self-update/event-poll) lives *inside* `dispatch.sh`'s while-loop, so the dispatcher itself was a single point of failure. Three deterministic-shell pieces close it (no merge/deploy/force-push anywhere):
    - **`bin/supervisor.sh`** — one watchdog pass, two scopes split by the cmux render constraint (below). `full` (launchd agent `com.loops.supervisor`, 60s; `loopctl supervisor install|remove|status|run`) supervises **the dispatcher only**: dead → revive via ⓪ reuse an already-queued **`⏳`-marked** 🔁 tab (only the intentional-queue marker counts — a marker-less un-materialized 🔁 tab may be a session-restored shell whose "reuse" is a no-op; a materialized-but-still-⏳ tab is a fired-and-died shell → closed) ① dashboard `/api/control start` proxy ② direct `loopctl start`, then verify the pid ~3s later. **Death vs spawn-blocked**: a "restart" only counts toward crash-loop when a real death is observed (`dispatcher.lastAlivePid` seen alive then gone, or new `dispatcher start (pid` lines in dispatcher.log beyond `dispatcher.startsSeen`); if neither signal fires the dispatcher never started (backgrounded cmux queue) → **spawn-blocked**: retry without counting/hold + rate-limited "foreground cmux" Telegram hint — this is what previously mis-escalated to a 30-min hold that blocked recovery. `panels` (called from dispatch.sh housekeeping ≤60s) supervises **dashboard + bot** from the dispatcher's PTY context, and runs **`sweep_panels`**: each panel records its own tab at boot via `cmux identify` (`state/panel.{dispatcher,dashboard,bot}.ref`), and the sweep closes every 🔁/📊/🤖-titled tab that isn't the recorded live one (plus all `⏹ loops *` exit-marked tabs) — this is what reaps the title-only shells a cmux app restart session-restores (worker tabs have their own pidfile/watchdog path; `🤖 loop builder` and user tabs are untouchable; missing ref file or empty list-workspaces → that class is skipped, flake principle). Intent markers `state/STOPPED.{dispatcher,bot}` (written by `loopctl stop` / dashboard stop actions, cleared by every start path) distinguish crash from deliberate stop — marked components are never revived. Dashboard "process alive but HTTP dead" → surfaced only, never killed (wedged philosophy). Actions append to `state/supervisor-events.jsonl`; alerts go out via **`bin/tg-notify.mjs`** (direct Telegram send, deliberately *not* through the bot — the bot is itself a supervised component), rate-limited per key. State: `state/supervisor.json`; opt-outs: `LOOPS_SUPERVISE_DASHBOARD=0`.
    - **Dispatcher-only queued-spawn exception** — `spawn-panel.sh` normally discards a workspace that fails to materialize (no-late-fire rule). With `SPAWN_PANEL_QUEUE_OK=1` (used *only* for the dispatcher by `loopctl start` and the dashboard `start` action) it instead leaves ONE tab queued, titled `🔁 loops dispatcher ⏳`, and exits 2: while the cmux app is backgrounded **no** new tab renders (escalation included), so discard-and-retry can never converge — the ⏳ tab auto-fires the moment the user foregrounds cmux, and the dispatch.sh double-start guard makes any duplicate firing harmless (dispatch.sh strips the ⏳ marker and records `state/panel.dispatcher.ref` + runs one immediate panels sweep at startup, and retitles its tab `⏹ loops dispatcher` on clean exit). Never use QUEUE_OK for workers/verifiers — they have no double-start guard.
    - **Crash-loop guard + self-update rollback** — ≥`LOOPS_CRASHLOOP_N`(3) dispatcher deaths within `LOOPS_CRASHLOOP_WINDOW`(600s): if the newest `state/.update_history` line (appended by self-update.sh on every ff) is <`LOOPS_ROLLBACK_WINDOW`(1h) old and HEAD == its result, the update is the suspect → `git reset --keep <prev-sha>` (local branch move only, uncommitted changes preserved — **not** a force-push, origin untouched) + write the bad sha to `state/.update_hold`, which self-update.sh refuses to re-pull until origin moves past it. Otherwise → `LOOPS_CRASHLOOP_COOLDOWN`(30min) restart backoff + escalate. Double-start guards in `dispatch.sh` (alive-pid check before claiming the pidfile) and `notify-bot.mjs` (pgrep self-check) make late-materializing duplicate spawns exit harmlessly.
    - **`bin/incident-bridge.sh`** (dispatch.sh housekeeping ≤120s) — turns engine-level failures into Backlog issues of the **engine self-improvement loop** (auto-detected: the enabled loop whose `repo` == LOOPS_HOME, e.g. `loops-improve`), which closes the full "self-fix + self-deploy" cycle: incident issue → worker fixes it (under the mission's syntax-check + core-path human-gate rules) → direct push → self-update → dispatcher re-exec. Signals filed: an orchestrator cycle failing `LOOPS_INCIDENT_FAILS`(2)+ consecutive runs (evidence = run.log tail), and supervisor `escalate`/`rollback` events. Deliberately **not** filed: `stuck` / `rework-exhausted` / **`auth/quota abort`** — the first two are per-issue *target-repo* problems the engine loop's worker cannot fix (and already have first-class human surfacing); `auth/quota abort` (a `run.log` tail matching `ACCOUNT_ABORT_RE` — weekly-limit / logged-out / invalid-key / low-credit) is a *claude account* state with no engine code to fix, so it skips **only** the cycle-error filing **without** consuming the streak/filed cursor (a genuine crash streak after the signature clears is still filed normally) — this is the basis for treating such aborts as environment noise, not engine defects. **But "not filed" ≠ "not surfaced":** an account block stops *every* loop at once with no issue and no dashboard banner, so **pass 0 (`account_alert`) runs before the filing gates** (Linear key / engine-loop detection) and sends a Telegram-only alert via `tg-notify.mjs`. It judges **current state**, not a streak (last run non-zero + `ACCOUNT_ABORT_RE` in the run.log tail + that run newer than `LOOPS_ACCOUNT_ALERT_MAXAGE`(4h), enabled and un-PAUSED loops only), fires **once globally** (accounts are shared — first match breaks), and re-alerts per signature every `LOOPS_ACCOUNT_ALERT_GAP`(6h). The signature is the claude message with the engine's trailing `[timestamp] =====` banner stripped, so it stays stable across cycles but changes when the reset time or account does. Placement matters: with the engine loop disabled the whole script `exit 0`s at the engine gate, which is exactly how a 4-day account-limit outage went completely unsignalled. Dedup = streak-reset for cycle errors + per-signature cooldown `LOOPS_INCIDENT_COOLDOWN`(86400s) for supervisor events, plus a global daily cap `LOOPS_INCIDENT_DAILY_MAX`(3). Creation via `bin/linear-create.mjs` (stdin description); state `state/incidents.json`; every filing is appended to the engine loop's `runs.jsonl` + Telegram-notified.
  - **Retro / hill-climbing** (config `retro:{everyCycles:N}`) — every N regular cycles dispatch.sh fires a `LOOP_MODE=retro` run (`retro-base.md`): analyzes merged-vs-closed outcomes, repeated review comments, human-gate precedents (`decisions/*.md`) and rewrites `state/learnings.md` (≤15 evidence-backed lines). Injected as `{{LEARNINGS}}` into orchestrator, worker, and validator prompts. **mission.md is never touched by the engine** — missions are human-owned; lessons live in the separate file, editable in the dashboard ⚙️ modal (with a manual "🧠 retro 실행" button / `run-retro` control action), and every update pings Telegram (comprehension-debt guard).
- **`dashboard-server.mjs`** — dependency-free Node HTTP server. `GET /api/status` aggregates each loop's `state/snapshot.json` + live cmux tabs + a 60s background `gh pr view` cache + a **60s background Linear statusType cache** (`refreshLinear`/`authStateOf`). The Linear cache exists because the PR cache was the *only* live signal: a `delivery:"direct"` loop never opens a PR, and a worker's live-TUI `claude` stays an idle process after finishing (so `worker-run.sh`'s exit hook — which removes the pidfile and retitles the tab `⏹` — doesn't fire, keeping the 🛠 tab `alive`). A finished direct-mode issue therefore showed **stale snapshot `In Progress` + alive tab = "작업중"** until the next cycle's cleanup, which can be many minutes since the reaper skips a loop while `/tmp/loop-<id>.lockdir` is held. `authStateOf(statusType, snapshotState)` reconciles the two: `completed`→Done, `canceled`→Canceled, `started`→In Progress **only if** snapshot is Backlog/terminal (otherwise the snapshot's custom started-state name — `In Review`, `Ready to Deploy` — is preserved, since statusType carries no name), `backlog|unstarted|triage`→Backlog only if snapshot claims progress/terminal. Derived `counts` (and thus the slot gauge), `stalled`, and `mergedInReview`/`closedInReview` all key off this. Read-only — it never moves Linear states. To respect Linear's per-key hourly rate limit it **reuses `event-poll.sh`'s already-fetched result** (`state/linear-states.tsv`, ≤90s old) and only queries the projects that file doesn't cover — note event-poll itself skips lock-held loops, so a busy loop falls back to a direct query, which is exactly the case that needs it. Dispatcher down → every project falls back to a direct query (observability must outlive the dispatcher). Failed/empty responses **keep the previous cache** rather than clearing it (same principle as the reaper's `TAB_TRUTH`). `POST /api/control` dispatches actions (`start`, `run-now`, `reconcile`, `resolve-gate`, `start-issue`, `toggle-enabled`, `set-schedule`, `build-loop`, `create-loop`, `save-mission`, `save-config`, …) by shelling out to the same `bin/` scripts and `cmux`/`gh`. It also serves pinned static assets at `/vendor/*` (filename-whitelisted) — Oat UI + a pinned MIT QR generator (`vendor/qrcode.min.js`, client-side in the 📱 원격 modal) + the PWA service worker/icons (`vendor/sw.js`·`icon-{192,512}.png`, served at root paths `/sw.js`·`/manifest.json`·`/icon-*.png` for SW scope). **Tailscale 원격(폰) + 웹푸시 (PWA) — `GET /api/remote`, control `remote-on`/`remote-off`, `/api/push/{key,subscribe,unsubscribe,test}` (`loopctl remote [tailscale|off]` · `loopctl dashboard remote` · dashboard ⋯→'📱 폰 원격 접속').** Enabling remote runs `tailscale cert <fqdn>` (writes `state/ts-remote.{crt,key}`, reused if <30d old) and opens **HTTPS** `https.Server`s (same `handler`) bound to the machine's tailscale IPs (`100.x`/`fd7a…`) **in addition to** the always-on `127.0.0.1` HTTP listener — tailnet-only, no LAN/public exposure, and it deliberately **does not touch `tailscale serve`** (the user may map it elsewhere → clobber risk; cert issuance is independent). HTTPS is required because iOS/Android **web push** needs a secure context. URL/QR = `https://<MagicDNS-fqdn>:<port>/`. **Web push** is hand-rolled zero-dep in **`bin/webpush.mjs`** (RFC 8291 aes128gcm via node:crypto ECDH-P256/HKDF/AES-128-GCM + RFC 8292 VAPID ES256 JWT — validated by an RFC 8291 Appendix-A round-trip self-test `node bin/webpush.mjs --selftest` and cross-checked against the `web-push` npm lib; **no** npm dep). VAPID keys + subscriptions + a `seen` diff-set live in `state/push.json` (gitignored); a 20s `pushTick` diffs `status()` attention (human-gate/rework-exhausted/stuck/CI…) and pushes **new** signals (first tick seeds silently; notification tap deep-links `/?loop=`). Persisted via `LOOPS_REMOTE=1` in loops.env (server auto-opens on boot; runtime toggle needs no restart). Auth: `authOK` trusts **only loopback** (cmux panel); any non-loopback/proxied request requires `LOOPS_REMOTE_AUTH="user:pass"` when set (optional — tailnet is already the private boundary). `dashboard.html` is a **mobile-responsive** single-file PWA UI (≤820px: sidebar→off-canvas drawer + `#mtop` topbar, cards/modals full-screen, safe-area insets): bespoke telemetry layout (sidebar/gauge/LED-dot/feed/cards) on top of **Oat UI** components (buttons, inputs, `.badge`, `role=alert`, `<ot-dropdown>` menus, native-title tooltips). The whole telemetry palette (dark + light via `data-theme`) is mapped onto Oat's CSS variables, so Oat components inherit the console look. Global controls (dispatcher start/pause/stop/logs + workspace settings) live in the `⚙️ 디스패처` `<ot-dropdown>`; per-loop `⚙️ 설정` vs global `워크스페이스 설정` (Linear key, Telegram bot) are separate modals.
- **`bin/notify-bot.mjs`** — optional Telegram remote bridge (zero-dep, `node:https`). One process, two loops: polls `GET /api/status` and diffs to **push** human-gate/PR/CI/cycle-error alerts to the owner's phone; long-polls Telegram `getUpdates` for **inbound** button taps / message replies / slash commands, mapping each to a `POST /api/control`. It is a full remote control, not just alerts: an interactive `/menu` (inline keyboards) navigates dispatcher→loops→tasks and exposes nearly every dashboard action — global `start`/`stop`/`pause`/`resume`/`awake`, per-loop `run-now`/`reconcile`/`loop-pause`/`toggle-enabled`, per-issue `resolve-gate`/`cancel-issue`/`cleanup-issue` — plus slash fallbacks (`/status` lists active In Progress/In Review tasks). Free-text messages that aren't slash commands or gate replies now run a **real agent**: `claude` headless (`-p`, capable model via `LOOPS_BOT_AGENT_MODEL`, default Sonnet) whose **only** toolset is the Loops control MCP server (`bin/loops-mcp.mjs`, a zero-dep stdio JSON-RPC server that thinly relays `/api/status`·`/api/session`·`/api/control` over 127.0.0.1). The agent multi-steps on its own — e.g. "seo에 'OG태그 누락 점검' 태스크 추가하고 바로 작업 시작해" → `get_status` → `create_issue{start:true}`; "요즘 CI 왜 깨져? 원인 보고 고칠 태스크 만들어" → `get_run_log`/`get_worker_screen` → several `create_issue`. `create-issue` (new `/api/control` action) creates a Linear Backlog issue in the loop's project via `issueCreate`, and with `start:true` immediately spawns a worker (mirrors dashboard `start-issue`); task-add follows the user's literal words (add-only vs add+start). The bot passes the MCP config **inline** (`--mcp-config <json>`), with `--strict-mcp-config` (ignore the user's global MCP servers) and `--disallowedTools Bash Edit Write NotebookEdit …` so the agent **cannot merge/deploy/force-push** — that's enforced structurally (no such tool exists), not by prompt. **The destructive actions `cancel_issue`/`cleanup_issue` are deliberately absent from the agent's toolset** — the agent proposes and points the user to the existing 2-tap confirm buttons / `/cancel`; it never cancels or cleans up on its own. The MCP server relays only the dashboard HTTP surface — it does **not** touch cmux — so the engine is unchanged. Auth = `TELEGRAM_CHAT_ID` lock (auto-paired on first message); token in `loops.env` (`TELEGRAM_BOT_TOKEN`, a preserved key). Launched via `loopctl bot` **or** the dashboard ⚙️ (token field + ▶ 봇 시작, backed by control actions `set-telegram`/`bot-start`/`bot-stop`; `GET /api/status` exposes `telegram:{configured,paired,running}` booleans only, never the token). **The bot never merges/deploys/force-pushes** — the destructive actions it exposes are `cancel-issue`/`cleanup-issue` (two-tap confirm); `resolve-gate` only relays the human's decision to the worker. Merging stays a human action.

## Product layer (optional, above loops)

`products/<id>/product.json` (gitignored — user data) groups multiple loops onto **one product = one Linear project** (e.g. PM loop on `linearLabel:"Feature"` + bug loop on `"Bug"`). Two mechanisms, both backward-compatible (no `product` field → 기존 단독 루프 동작 그대로):
- **Config inheritance** — a loop config with `"product": "<id>"` inherits `repo, baseRef, prBase, claudeCmd, linearProjectId, linearProjectUrl` from product.json (loop value always wins; whitelist only — `bin/loop-config.mjs`, mirrored inline in `_common.sh` `cfgval`; consumers: cfgval(shell 전부)·render-prompt·dashboard-server). ⚠️ **Inheritance keys on `cfg[k] == null`, so an empty string permanently blocks it** — `repo:""` does not fall back to the product, it just makes the loop unrunnable (`fatal: not a valid object name: 'origin/develop'` on the first spawn). This bit twice via the dashboard: `GET /api/config` returns the **raw** loop config, so inherited fields render blank in the ⚙️ modal, and saving wrote those blanks back as `""`. `save-config` now **deletes** any key submitted empty instead of storing `""`, and the modal shows the inherited value as a `placeholder` (from `GET /api/config?loop=<id>&effective=1`, placeholder-only — putting effective values in the form's `value` would copy product settings into the loop config and silently freeze future product changes). Loop-specific settings (schedule/cap/label/worktrees/enabled) stay in the loop config.
- **`bin/triage.sh` (product-level classifier)** — dispatch.sh polls ≤60s per product: unlabeled inbox issues (no route label; `bin/linear-inbox.mjs`) are classified by a cheap headless claude call (`triage.routes` in product.json; MCP 0 · tool 0 — the LLM only *picks* `{"label","reason"}`, the deterministic `bin/linear-label.mjs` applies it and rejects labels not in routes) → the moment the label lands, that label's loop event-poll (`on.linearNew`, label-scoped) pulls an immediate cycle. Per-issue 3-attempt cap → give-up comment ("라벨 직접 지정"). Dedup is Linear itself (라벨 부재 = 미분류); local state (`products/<id>/state/triage.json`) holds attempts only. No merge/state-moves/issue-creation — label+comment only.

## A loop's anatomy

`loops/<id>/` (gitignored — user data) contains:
- `config.json` — schema: `id, name, emoji, repo, baseRef (origin/develop), prBase (develop), branchPrefix, orchestratorWorktree, worktreePrefix, linearProjectId, linearProjectUrl, maxWorkers, backlogTarget, schedule{startAt,intervalSec}, enabled, claudeCmd, delivery` + opt-in feedback-layer fields: `verify (bool), validate (bool), budget{dailyUsd}, on{ciFailure,prReview,linearNew}, retro{everyCycles}, measure{baseUrl, previewUrlRegex, login, viewport, waitSec, minRoot, lighthouse{runs,preset}, thresholds{bytesPct,requests}, routes[{id,path,selector?,minRoot?,lighthouse?}]} (실측 층 — 있으면 발굴·검증이 실제 브라우저 측정 기반이 된다)` + shared-project/drain fields: `linearLabel (str — 하나의 Linear 프로젝트를 라벨로 나눠 여러 루프가 공유; 지정 시 조회·발굴·fan-out·정리·이벤트가 그 라벨로 스코프되고 새 이슈에 라벨 부여; `linear-states.mjs`의 옵션 인자로 결정론 층에, `{{LINEAR_LABEL_NOTE}}`로 프롬프트 층에 주입; 비면 프로젝트 전체=기존 동작), drain{discoverySec} (bool|obj — "쌓이면 계속, 비면 조용": `dispatch.sh`가 스케줄 발사를 값싼 Linear 체크(`linear-drain-check.mjs` — run-log·human-gate 이슈는 드레인 불가로 제외)로 게이트 — 드레인 가능 backlog>0 & in-flight<cap 또는 발굴 주기 도래일 때만 사이클, 아니면 스킵→idle 토큰비용 0)`. See `examples/*/config.json`, `examples/bug-drain/`, and the README field table.
- `mission.md` — injected as `{{MISSION}}` into the orchestrator prompt; defines *what work to discover and how* (the only domain-specific logic).
- `state/` — runtime: `snapshot.json` (dashboard reads this — orchestrator writes it in STEP 4), `runs.jsonl` (append-only event feed), `run.log`, `next_fire`, `decisions/<ISSUE>.md` (human-gate resolutions), `PAUSED`, `costs.jsonl` (headless-run usage), `rework.json` (review-rework counters), `events.json` (event-poll cursors), `linear-states.tsv` (event-poll's last Linear statusType table, reused by the dashboard's live-state cache), `verify/<ISSUE>.json` (verifier verdicts), `validate/<ISSUE>.json` (validator verdicts), `learnings.md` (retro lessons → `{{LEARNINGS}}`), `liveness.json` (watchdog).

The Linear project **is** the state machine (dedup across runs): `Backlog → In Progress → In Review → Done/Canceled`. A "run log" tracking issue per loop gets one comment per cycle.

## Conventions that matter when editing

- **Never merge / deploy / force-push** from engine code or prompts. Workers open PRs only; merging is the human gate. Preserve this in any prompt or script change. **Exception (opt-in):** a loop with `"delivery": "direct"` in its `config.json` makes its workers push straight to `prBase` (non-force, rebase-then-push, stop on conflict) instead of opening a PR — used for personal/no-reviewer repos like the `loops-improve` self-improvement loop. Default (no `delivery` field) = `"pr"` = the safe PR flow. `render-prompt.mjs` swaps the worker's step 4–7 (`{{WORKER_DELIVERY}}`) and an orchestrator note (`{{DELIVERY_NOTE}}`) based on this flag. **force-push stays banned in both modes.**
- **No silent fallback.** Both base prompts forbid `?? default`, swallowed catches, and guessing — fix root cause. The target repos enforce this via their own CLAUDE.md/AGENTS.md (which workers/orchestrators must obey, since cwd is the *target* repo's worktree, not this one).
- **`spawn-orchestrator.sh` must stay foreground** (the caller backgrounds it). Detaching loses cmux socket access, so workers can't spawn — hence the repeated "FOREGROUND / cmux 안에서 실행" warnings.
- **cmux lazy-PTY: a tab's command only starts once the tab actually renders on screen.** `new-workspace --command` merely queues "text+Enter"; from a non-cmux caller (launchd, an external shell) — or into a window that's minimized / on another Space — the workspace object is created but no PTY exists, so the command silently waits and fires **much later** when the tab first renders (the double-dispatcher hazard). Therefore every panel spawn goes through **`bin/spawn-panel.sh`**: create → verify materialization (`read-screen`) → escalate (select → app activate → new-window+move+focus) → on final failure **close the workspace** (so nothing fires late) and exit non-zero. `loopctl start|dashboard|bot|run-now` all use it, and — since GOD-59 — so does `spawn-worker.sh` (workers spawn via spawn-panel too, so an un-materialized 🛠 tab can't wedge an In Progress slot), but **without** `SPAWN_PANEL_QUEUE_OK` — workers have no double-start guard, so the queued-spawn exception stays dispatcher-only. This constraint is also why supervisor `full` revives the dispatcher via the dashboard proxy first, and why the `panels` scope runs from inside dispatch.sh rather than launchd.
- **PR URLs come only from `gh pr view --json url`** — never construct `org/repo` URLs by hand (origin may be a GitHub mirror).
- **`claudeCmd` 래퍼 계약.** per-loop config의 `claudeCmd`는 `claude` 자리에 래퍼를 허용한다. ⚠️ 값은 `${=CLAUDE_CMD}`로 **공백 분리**되며 따옴표를 해석하지 않는다 — `claude-acct cloop`(2단어)나 `env K=V claude`(3단어)는 되지만 공백 있는 인용 인자는 깨진다. 현재 전 loop이 `claude-acct cloop`(dotfiles 제공: 멀티계정 라운드로빈 + 리밋 핸드오프. 리밋 순간 limit-marker 훅이 무인 세션의 claude를 종료시키고(`CLAUDE_LIMIT_AUTOEXIT=1`), 래퍼가 transcript를 다음 계정으로 복사해 **원래 플래그를 보존**한 채 `--resume` — verifier의 `--disallowedTools` 구조 가드도 유지된다). 이 재개를 위해 래퍼가 인자를 파싱하므로, 엔진의 claude 호출부(`run-once.sh`·`worker-run.sh`·`verifier-run.sh`·`validator-run.sh`)에 **값을 소비하는 새 플래그를 추가하면 dotfiles `cloop`의 case 목록에도 추가**해야 한다(모르는 값-플래그의 값은 프롬프트 위치인자로 오인돼 재개 시 버려짐). 역방향 계약: 래퍼는 stdout을 오염시키면 안 된다 — headless 호출자는 `--output-format json`의 JSON 정확히 1개를 기대한다(`record-cost.mjs`). **`cloop`은 zsh 함수라 그대로는 비대화형 스크립트에서 안 보인다** — dotfiles의 `claude/claude-acct`(→ `~/.local/bin/claude-acct` 심링크, `LOOPS_PATH_PREPEND`에 그 경로가 있어야 함)가 `claude-multi.zsh`를 source 해 함수를 실행 파일로 노출하는 진입점이다. 이 심링크가 없으면 claudeCmd는 조용히 `command not found`가 되므로, **계정을 특정 dir로 하드코딩(`env CLAUDE_CONFIG_DIR=… claude`)하면 그 계정 한 곳이 한도에 걸리는 순간 전 loop이 동시에 멈춘다** — 실측으로 4일 정지했다. 계정 전환/제외는 loops 설정이 아니라 dotfiles 쪽 `cstat`/`con N`/`coff N`(라운드로빈 대상, `~/.claude-tokens/rr-accounts`)에서 한다.
- Concurrency: `in-flight = (In Progress) + (In Review)`; cap = `min(maxWorkers, LOOP_MAX_WORKERS)`. Per-loop run lock is a `/tmp/loop-<id>.lockdir` mkdir.
- **human-gate**: an issue whose body says "human-gate" is *not* implemented by a worker — it surfaces to the dashboard (🔴) for a human decision, which is written to `state/decisions/<ISSUE>.md` and injected back into the worker as an authoritative override on the next spawn.
- **Terminal-state cleanup.** Once an issue reaches a terminal state — `Done` (PR merged) or `Canceled` (PR closed / user discarded) — its cmux tab + git worktree + branch are removed automatically. This runs deterministically in `bin/run-once.sh` *after* the headless orchestrator (every cycle, all `LOOP_MODE`s) via `bin/cleanup-issue.sh <loop> <issue>` — idempotent, matches the cmux tab by title (`🛠/↩ <loop> <issue>`), gated on the worktree dir actually existing. ⚠️ **`cmux list-workspaces` intermittently returns an empty list** (RPC flake — bursts of empty responses measured between healthy ones). `cleanup-issue.sh` treated that as "no tabs to close", so it removed the worktree+branch, logged `cleaned`, and left the tab forever — and because the worktree was then gone, nothing re-matched it. This is the root cause of "merged PR's cmux workspace never closes". It now retries the listing 3× and, if still empty, **says so loudly** instead of silently succeeding (`close-workspace` failures are surfaced too); the tab is reclaimed on the next reaper pass, which still matches it via `TAB_REFS` because the issue is terminal. `cleanup-terminal.sh` already had this guard (`TAB_TRUTH`) — the two are now consistent. The same helper backs the dashboard `cancel-issue` ("🗑 버리기") and a per-issue "🧹 정리" button; `bin/cleanup-loop.sh` (dashboard `delete-loop` and `loopctl cleanup <loop>`) sweeps a whole loop. **In-progress worktrees (In Progress / In Review) are still preserved** so a user can `claude --resume` them; the LLM prompts never do this cleanup (deterministic shell only); **force-push / merge / deploy stay banned.** The orchestrator always rebuilds its own worktree from `baseRef` (never the user's working tree).
- **Liveness & stall recovery is deterministic, keyed on Linear (not the stale snapshot).** Two shell loops run in `dispatch.sh` every ≤60s. The **watchdog** skips a loop entirely while its `/tmp/loop-<id>.lockdir` is held (it spawns heal workers — racing fan-out would bypass the cap). The **reaper** used to do the same, but a loop whose cycle outlasts its interval (e.g. `intervalSec:120` with 8–10 min cycles) holds the lock almost continuously, so the reaper never ran and finished workers' tabs/worktrees piled up until the cycle ended. It now runs in **terminal-only mode** (`CLEANUP_TERMINAL_ONLY=1`) while the lock is held: terminal (`completed`/`canceled`) issues are never fan-out targets, so cleaning them can't race. Ghost reclaim, Backlog-litter reclaim, orphan-tab closing and validator/verifier sweep stay lock-gated because they **do** race — the orchestrator moves Linear to In Progress *before* spawning (`spawn-worker.sh:45`), so during fan-out a legitimate issue transiently looks like a no-tab/no-worktree ghost, and reclaiming it would cancel the fan-out:
  - **`bin/watchdog.sh`** — the in-flight set is **Linear `started`** (always fresh; the old code keyed on existing-worktrees + hourly `snapshot.json`, which missed no-worktree ghosts and lagged a full cycle). ⚠️ A cmux tab does **not** reliably die with its `--command` — the pane can drop to a bare shell, and a cmux **app restart session-restores title-only shell tabs** (dead worker looks alive → wedged false-positive + heal blocked). So liveness is process-based: `worker-run.sh` writes `state/live/<ISSUE>.pid` on start, and on exit removes it + retitles its tab **⏹** (out of the `🛠|↩` liveness regexes; cleanup-issue/loop sweep ⏹ too). Per `started` issue: *branch has any PR* (delivered — In Review or awaiting Done/Canceled reconcile) → not watchdog's concern, **except** the pidfile corpse check still runs: with resident monitors an In Review issue keeps a live 🛠 tab, and a cmux-restart corpse there would permanently block rework/heal's live-tab dedup (`close_if_corpse`). *Live tab* (no PR yet) → first, if a pidfile exists and its pid is dead, the tab is a corpse → watchdog closes it and lets the next pass heal (since GOD-59, the **no-pidfile** case is also reclaimed: no pidfile + worktree present + 0 commits ahead of `baseRef` + `CORPSE_PASSES` consecutive empty read-screens → an un-materialized corpse → `close_if_dead_shell` closes the tab, next pass heals; any pidfile / commit / non-empty screen resets it, so a slow-but-fine worker is never touched); else `cmux read-screen` hash; if the screen is frozen ≥ `LOOP_WEDGE_SEC` (300s) it's **`wedged`** (surfaced only — never auto-killed, to avoid killing a slow-but-fine worker). *No tab* → if a branch **open PR** exists (pr-mode) it's In Review (done, awaiting human merge → leave it); else it's a dead In Progress — if a **worktree remains** (progress) → `bin/heal-worker.sh` resumes it in place (grace → `LOOP_HEAL_MAX` attempts → `escalated`), if **no worktree** it's a ghost the watchdog does **not** re-spawn (would bypass the cap).
  - **`bin/cleanup-terminal.sh` (the reaper)** — beyond terminal cleanup, when Linear is fresh it also (4) reverts **no-worktree `started` ghosts → Backlog** via `bin/linear-move.mjs` (a ghost pins `in-flight` so `capacity = cap − in-flight` goes ≤0 and the orchestrator stops spawning — this is the usual "loop silently stops"; reverting frees the slot so the orchestrator re-spawns within cap), and (5) reclaims **Backlog-issue worktree litter** (dead worker reverted to Backlog, no live tab/PR) via `cleanup-issue.sh`. Both gated on live Linear + no open PR; `escalated` issues are vetoed. **Backlog moves are not merge/cancel — the no-merge rule is intact.**
  - The dashboard reads `state/liveness.json` and surfaces `stuck` (escalated), `wedged`, and `healing`. The orchestrator prompt now **defers** dead-worker handling to these loops (LLM is a rare backstop), so it no longer races them.

## Adding a loop

Prefer the **`create-loop` skill** (or dashboard "+ 새 loop" → `bin/build-loop.sh`), which follows `bin/loop-builder.md`: it creates a Linear project, writes `mission.md` + `config.json` under `loops/<id>/`, and leaves it `enabled:false` for human review. Manual path: copy an `examples/<...>/` dir to `loops/<id>/` and fill in repo / Linear IDs / worktree paths.
